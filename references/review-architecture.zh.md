# 按需评审架构

[English](review-architecture.md)

用户调用 birdview-review，或要求优化架构、评审模块边界、寻找架构重构机会时使用，不要求点名 Birdview。引文中出现相关词语或讨论如何实现本技能，不算评审请求。按[约束发现](constraints.zh.md)检查生效规则，再调查指定范围。有已核验地图就复用；独立评审不要求全项目建图或完整约束清单。普通编码、局部重构、仅画架构图和自动模式不触发评审。

## 检查职责

存在相关项目术语和架构决策时先阅读；缺少术语表或 ADR 不代表需要创建。追踪候选模块的调用方与实现，寻找具体问题：

- 一个职责需要跨多个模块协同修改，或调用方必须了解内部顺序、错误处理、配置细节。
- 包装层没有增加多少行为，却多引入一层接口。考虑移除它后复杂度是消失了，还是转移到调用方；小型适配器也可能有存在价值。
- 现有边界让重要行为难以通过公开接口验证。说明受影响的行为，不要求为每个实现细节编写测试。

优先考虑让调用接口更简单、相关行为更集中的改动。模块数量、文件大小和图是否整齐本身不构成问题证据。尊重已有架构决策；只有具体的新证据才支持重新讨论，并应明确指出冲突。

## 提出有依据的候选方案

仅返回有依据的候选项，最多 6 个，按预期价值排序。每项提供：

- 现状图：源码中实际存在的调用方、模块和步骤，每个模块和步骤都有证据。每个判断写成一条红笔批注，类型为 duplicate、leak、shallow、ordering 或 missing-seam 之一，附简短手写说明和各自的判断强度（observed 或 hypothesis）。
- 调用方现在要记住什么、改完后还要记住什么（callerKnowledge）。这就是方案声称要收窄的 Interface 宽度；写具体义务，不写形容词。
- 誊清稿：加深后的模块写成 deep 节点，并列出它吸收的现状图节点，以及保留的接缝。
- 删除测试（保留、删除或收窄）、用术语表词汇表达的收益（局部性、杠杆、深度、接缝、可测性）、不改变的边界、迁移代价，以及通过 Interface 验证的行为。
- 推荐强度（证据有力、值得探索、推测）与单条批注的判断强度分开。指出缺失证据，不把假设当成缺陷。

## 生成与交付

按[评审契约](review-contract.zh.md)写入项目的 .birdview/review.json，然后带引用核对渲染：

```sh
node <skill-root>/scripts/render-review.mjs .birdview/review.json .birdview/review.html --repo .
```

引用前先读源码文件。引用是所注行范围的原文，`--repo` 会拒绝任何不一致；出错时修正证据，不要放宽引用。标题先讲业务；导语和业务影响解释后果，两张图的图注分别写当前后果和预期结果。文字不超过契约里的长度限制，它们就是版面限制。同一事物在两张图里使用相同节点 id。记录源码提交、未提交文件和读过的依据。

打开 HTML，检查桌面、手机、两种主题、红笔批注和可读性，报告实际预览结果及缺口。只交 JSON 不算交付。允许空候选列表并交代已检查范围，不凑数量。

向已有架构页添加评审入口时，绑定 mapId、revision 和源码提交，再运行：

```sh
node <skill-root>/scripts/render.mjs .birdview/architecture.json .birdview/architecture.html --review .birdview/review.json --repo .
```

保留已有活动参数及 --constraints 参数。命令生成同目录 .review.html 并添加导航链接，保留架构、约束布局。模块绑定会被校验。建议不能覆盖当前架构或编造 editing 事件。

## 确认后实施

展示候选，证据支持时推荐一项。询问实施哪项具体方案，然后停止等待答复。评审请求和生成页面不代表批准。同一已展示范围的明确批准继续有效；尊重用户明确跳过确认的指令。实施按[变更流程](show-changes.zh.md)执行，仅依据验证后的真实改动更新当前地图，报告检查结果及缺口。应用旧建议前复核源码版本。首版没有自动执行或实施状态追踪。
