本轮基线架构评审功能刚加入，本轮把它连同已有的交付与约束代码一起视为当前状态。

建议先做01 · 项目页交付分成两条入口评审功能刚加入，现在把评审输出并入 deliver 的成本最低，并能直接获得已有的别名与原子写出保证。
01

项目页交付分成两条入口

带评审的项目页只能走 render.mjs，而 birdview deliver 才有别名防护与原子写出；两条入口各自解析参数、判断别名、写文件。

证据有力 · 依赖：可用本地替身 · 业务影响：用 --review 重新交付时失去 deliver 的别名检查和“主页最后发布”保证，写到一半失败会留下新旧混杂的页面组；以后每加一种输出都要改两处。

图号01 / 现状批注4依据源码 10 处

两个 CLI 各管一套参数、别名与写出规则，评审只能走较弱的那条。

  1. ①
    别名检查两套已观察

    deliver 用 realpath 与 inode 识别别名，render.mts 只比较 path.resolve 后的小写字符串，符号链接或硬链接输出可能绕过后者。

  2. ②
    写出保证不一致已观察

    delivery.md 承诺临时文件、主页最后发布；render.mts 按 html、review、sources 顺序直接写，失败时可能只更新部分文件。

  3. ③
    deliver 无评审口已观察

    deliveryUsage 没有 --review；评审的项目名、mapId、revision 与模块绑定检查只存在于 render.mts 的 isMainModule 分支，其他调用方无法复用。

  4. ④
    activity 解析两份已观察

    activity JSONL 的逐行解析与报错文本在两个入口逐字复制。

调用方现在要记住：

  1. 评审只能走 render
  2. render 非原子写
  3. 别名防护强弱不同
  4. 两套参数规则
  5. 输出文件名推导

收拢之后只剩：

  1. 传 --review 即可

同一段 activity 解析

方案

把 deliver() 扩展为唯一的项目页交付函数，接收可选评审输入并复用其别名检查与原子发布，render.mts 主块只解析参数后调用它。

删除测试 · 收窄

删掉 render.mts 主块的交付逻辑后复杂度并未转移给调用方，而是合并进 deliver()；render.mjs 仍保留 --simulation 等诊断入口，只是变窄。

不改变

  • renderArchitecture 与 renderReview 的签名和页面结构
  • review.json 契约
  • --simulation 路线

收益

  • 局部性别名、绑定、写出规则只在一处修改
  • 杠杆deliver 新增评审输出，一次实现两条入口都受益
  • 可测性评审绑定检查可通过 deliver() 回执直接测试

迁移代价

中等：需调整 deliver 参数表与回执字段、迁移 render.mts 主块测试；评审功能刚加入，现在合并比用户依赖后再迁移便宜。

通过 Interface 验证

  • deliver 带 --review 时输出 project.review.html，并在回执 written 中列出
  • 评审输出与输入同名或经符号链接指向输入时被拒绝且不写任何文件
  • 评审绑定过期时回执 ok 为 false，原有页面保持不变
02

规则合法性校验散落三处

已审查规则目录没有统一的校验入口：编译不校验，历史收集、规则视图、来源视图各写一份范围与字段检查，条件还不一致。

值得探索 · 依赖：进程内 · 业务影响：坏规则要到渲染阶段才报错，且不同视图对同一条规则的接受标准不同；新增规则字段或适用性取值时容易漏改某一处。

现状图据源码绘制 · 红笔为评审批注

图号02 / 现状批注3依据源码 6 处

同一套规则约束写了三遍，复用路线几乎不校验，错误推迟到渲染。

  1. ①
    范围校验写三遍已观察

    行号范围、必填字段与适用性枚举在历史收集、规则视图、来源视图各写一次；来源视图不要求 category，历史收集额外检查路径格式，三处标准已经分叉。

  2. ②
    错误推迟到渲染已观察

    compileConstraintRules 只解析锚点，不检查 name、explanation、verification 等字段；缺字段的规则会被写入 constraints.json，直到渲染才失败。

  3. ③
    复用只查形状已观察

    --constraints 复用时 deliver 只确认 rules 是数组，render.mjs 直接类型断言，真正的校验依赖下游视图碰巧执行。

调用方现在要记住：

  1. 哪个视图会报错
  2. 来源视图不查分类
  3. 编译后仍可能坏
  4. 复用需自行检查

收拢之后只剩：

  1. 校验失败即停

方案

在 constraint-types 旁新增 validateReviewedCatalog，编译结束与 --constraints 复用时调用，三个下游检查改为依赖其结果。

删除测试 · 可删除

删除三处内联检查后，复杂度移入一个校验函数而不是调用方；下游代码变短，失败时机提前到读入或编译。

不改变

  • constraint-catalog 与 reviewed-rules 的文件格式
  • 规则视图与来源视图的页面内容
  • Git 行段历史算法

收益

  • 局部性新增适用性取值或字段只改一处
  • 可测性规则合法性可脱离渲染直接测试

迁移代价

低：纯进程内重构；需确认来源视图是否有意接受无 category 的规则，若是则在校验中显式区分。
